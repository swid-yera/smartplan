# KPI Help Solve

## Проблема

Пользователи с ролью `teacher` не понимают, как работать с KPI в EduPlan.

Главная точка боли не в самой отправке данных, а в выборе правильного пути:

- какую категорию выбрать;
- какие данные нужно заполнять;
- как именно заполнять поля;
- что делать после отправки на проверку;
- почему запись могли отклонить.

Из-за этого преподаватель теряется в интерфейсе, делает ошибки при заполнении и несколько раз возвращается к одному и тому же шагу. В результате:

- выбирается неверная категория;
- часть полей заполняется не так, как нужно;
- запись уходит на доработку;
- методист получает лишнюю нагрузку;
- KPI воспринимается как сложный и тяжёлый процесс.

Видео-курс здесь не лучший вариант. Он дорогой по времени, тяжёлый в производстве и плохо помогает в момент, когда пользователю нужно быстро принять решение.

## Что уже есть в проекте

По коду видно, что KPI в системе уже частично поддержан:

- `/kpi/entry` показывает список категорий для ввода данных;
- `/kpi/guides` уже содержит общий обучающий материал по KPI;
- `/kpi/categories/:id` показывает описание категории, список допустимых типов и количество полей;
- форма создания KPI по категории уже умеет валидировать обязательные поля, URL, будущие даты и файлы;
- `docs/eduplan_criteria_distribution.md` уже содержит сопоставление критериев с категориями.

То есть данные для помощи уже есть. Проблема не в отсутствии информации, а в том, что она показана не в том месте и не в том формате.

## Что можно сделать без масштабных изменений backend

Это можно решить в основном на фронтенде, потому что нужные данные уже приходят в интерфейс:

- категории загружаются через `services.categories.getAllOptions()` и `services.categories.getByIdOptions()`;
- у категории уже есть `name`, `description`, `awardTypes`, `awardTypesExpanded`, `fieldsExpanded`;
- форма создания записи уже знает, какие поля обязательные, какие типы полей использовать и как отправить данные;
- часть валидации уже выполняется на клиенте;
- общий KPI-guide уже существует, значит отдельный курс строить не нужно.

Вывод простой: **backend можно оставить почти без изменений**. Достаточно переупаковать информацию на фронте так, чтобы преподаватель видел не “список сущностей”, а “что делать дальше”.

## Почему текущего UX недостаточно

- На `/kpi/entry` преподаватель видит только набор категорий, но не понимает, какая из них подходит под его награду.
- Tooltip или короткое описание категории слишком слабые для новичка и плохо работают на мобильных устройствах.
- Общая страница `/kpi/guides` объясняет систему в целом, но не отвечает на главный вопрос: “куда отнести мою награду?”
- Страница категории помогает уже после открытия, а пользователь сначала должен угадать, куда нажать.

## Моё мнение

Лучшее решение здесь не отдельный курс, а **лёгкая встроенная помощь прямо в KPI-сценарии**.

То есть не обучение вне системы, а подсказка в момент выбора.

## Решение без backend-изменений

### 1. Добавить на `/kpi/entry` короткий помощник выбора категории

Перед списком категорий нужен компактный блок:

- 3-4 шага: `выбери результат -> найди подходящую категорию -> заполни поля -> отправь на проверку`;
- короткое объяснение, что считается правильной категорией;
- быстрые фильтры по типу достижения;
- ссылка “не знаю, куда отнести” с понятным маршрутом помощи.

Это можно сделать без backend:

- взять список категорий с уже существующего `GET /categories`;
- на фронте сгруппировать их по смыслу;
- использовать существующие локали и `docs/eduplan_criteria_distribution.md` как основу для подсказок;
- при необходимости держать простую карту `событие -> категория` в frontend-конфиге или JSON.

### 2. Превратить категории в “карточки-ответы”

Каждая категория должна отвечать не только на вопрос “как называется”, но и на вопросы:

- когда её выбирать;
- какие достижения сюда относятся;
- какие документы или подтверждения нужны;
- какие поля обязательны;
- какие типовые ошибки бывают;
- как понять, что запись готова к отправке.

Сейчас категория показывает название и описание, но для преподавателя этого мало. Нужен более прикладной смысл.

Это тоже можно сделать без backend:

- расширить карточку категории на фронте;
- использовать `category.description` как основной текст;
- добавить блоки “подходит, если”, “что приложить”, “какие поля заполнить”;
- если данных нет на сервере, держать короткие пояснения в локальном frontend JSON.

### 3. Сделать лёгкий “мастер выбора”

Это может быть простой сценарий из 3-4 вопросов:

- что у вас есть: награда, сертификат, публикация, участие, открытый урок, конкурс, стажировка;
- к какому результату это относится;
- есть ли подтверждающий документ;
- нужны ли дополнительные поля.

После ответов система должна:

- подсказать подходящую категорию;
- показать, какие поля нужно заполнить;
- дать ссылку сразу в нужную форму.

Это самый полезный вариант без backend-изменений, потому что мастер можно собрать как обычный client-side flow:

- первый шаг: тип достижения;
- второй шаг: уточнение по факту награды или документа;
- третий шаг: вывод подходящей категории;
- четвёртый шаг: переход в существующую форму `/kpi/categories/:id/create`.

### 4. Заменить длинные материалы на микроформаты

Вместо видео лучше сделать набор коротких форматов:

- краткая инструкция на 1 экран;
- FAQ “что делать, если…”;
- примеры заполнения;
- скриншоты или короткие GIF;
- чек-лист перед отправкой;
- список частых ошибок.

Это дешевле в поддержке, быстрее обновляется и лучше читается.

С технической точки зрения это можно хранить как:

- статические `locale.json` в `frontend/src/app/kpi/...`;
- отдельный markdown или JSON для помощи;
- небольшие карточки, drawer или panel-компоненты на фронте.

### 5. Встроить подсказки в форму ввода

Когда преподаватель уже открыл форму записи, рядом с полями должны быть:

- краткое пояснение, зачем это поле нужно;
- пример значения;
- отметка обязательности;
- предупреждение о типичной ошибке;
- кнопка “показать пример заполнения”.

Это особенно важно для полей, которые вызывают сомнение:

- название достижения;
- дата;
- файл подтверждения;
- описание;
- ссылка;
- количество;
- тип результата.

Для этого backend тоже не нужен:

- поля уже описаны в `fieldsExpanded`;
- тип поля уже известен (`text`, `number`, `date`, `url`, `file`, `select`, `multi_fields`);
- часть ошибок уже ловится на клиенте;
- сухие toast-ошибки можно превратить в понятные inline-подсказки.

## Что именно я бы оставил без backend-изменений

### Оставить как есть

- модель KPI и сущности категорий;
- эндпоинты категорий, типов и наград;
- текущую серверную валидацию и сохранение;
- маршрут `/kpi/guides`.

### Менять только на frontend

- страницу `/kpi/entry`;
- карточки категорий;
- страницу категории `/kpi/categories/:id`;
- форму создания записи `/kpi/categories/:id/create`;
- форму редактирования записи `/kpi/:id/edit`;
- тексты подсказок, FAQ, чек-листы, примеры;
- guided flow или мини-мастер выбора категории;
- обработку ошибок и pre-submit UX.

### Что можно показать без изменения API

- какую категорию выбрать;
- какие поля заполнять;
- что приложить;
- как понять, что запись готова;
- что делать при отклонении.

### Что можно добавить позже, если захочется усилить систему

- отдельные поля помощи по категориям на backend;
- рекомендации по заполнению на уровне категории;
- примеры заполнения на сервере;
- полноценный API для мастера выбора.

Но для первого этапа это не обязательно.

## Как бы я выстроил внедрение

### Первый этап

Самое быстрое и дешёвое улучшение:

- добавить на `/kpi/entry` блок “как выбрать категорию”;
- сделать короткие примеры по категориям;
- добавить FAQ;
- сделать явную ссылку на `/kpi/guides`;
- улучшить текст на карточках категорий.

### Второй этап

Сделать категориальный помощник:

- показывать “для чего категория нужна”;
- добавить “подходит, если у вас…”;
- добавить “не подходит, если…”;
- привязать это к уже существующим данным категорий;
- при необходимости держать простую матрицу соответствия в frontend JSON.

### Третий этап

Сделать guided flow:

- выбор события;
- подбор категории;
- автоподсказка по полям;
- предпросмотр перед отправкой;
- проверка типовых ошибок.

Этот этап тоже можно реализовать без backend, если правила сопоставления категорий заранее понятны и не зависят от сложной серверной логики.

## Почему это лучше видео

- дешевле в поддержке;
- быстрее внедряется;
- сразу работает в нужной точке сценария;
- не требует проходить обучение заранее;
- легко обновляется вместе с изменением категорий;
- лучше подходит для повторяющегося процесса, который пользователь выполняет каждый раз при новой награде;
- не создаёт лишней нагрузки на backend.

## Что уже есть как основа данных

Для наполнения подсказок уже есть хорошая база:

- `docs/eduplan_criteria_distribution.md` — матрица соответствия критериев и категорий;
- `frontend/src/app/kpi/categories/[id]/page.tsx` — место, где уже можно показать расширенную карточку категории;
- `frontend/src/components/cards/category-card.tsx` — точка входа в карточки категорий;
- `frontend/src/app/kpi/guides/page.tsx` — общий справочный слой;
- `frontend/src/app/kpi/entry/page.tsx` — лучшее место для практического помощника;
- `frontend/src/app/kpi/categories/[id]/create/page.tsx` — форма, где можно добавить пошаговые подсказки.

Это и делает решение реалистичным: нужная информация уже есть, вопрос только в том, как показать её преподавателю в правильный момент.

## Итог

Проблема решается не новым курсом, а **лёгкой встроенной системой помощи**.

Мой вывод:

- оставить `/kpi/guides` как общую справку;
- сделать `/kpi/entry` основным местом помощи для преподавателя;
- добавить понятные подсказки по категориям и полям;
- использовать короткие инструкции, примеры и мастер выбора вместо видео;
- не трогать backend без необходимости.

Если цель — чтобы преподаватель быстро понял, куда выбрать и что заполнить, то это самый практичный путь.

Главное: **это можно реализовать почти полностью на frontend, сохранив backend как источник данных и валидации**.
