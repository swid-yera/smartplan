# План импорта РУП из `.docx`

## Цель

Нужно дать пользователю возможность загрузить уже существующий РУП в формате `.docx`, автоматически разобрать его и создать в `EduPlan` новый РУП в статусе `DRAFT`, без ручного заполнения формы и без AI-генерации содержимого.

Пример входного файла:

- `docs/ПМ6 РУП Т22-4Б 288ч 2025-2025 уч год (1).docx`

## Что уже есть в проекте

### Frontend

- уже есть блок РУПов: `/rups`, `/rups/create`, `/rups/[id]`, `/rups/[id]/language-generation`
- уже есть UI для отслеживания длительного процесса по этапам:
  - `frontend/src/app/rups/[id]/language-generation/page.tsx`
  - `frontend/src/app/rups/components/language-generation-notifier.tsx`
- создание РУПа сейчас идет через JSON-запрос на `POST /rups`:
  - `frontend/src/services/rup.service.ts`
  - `frontend/src/app/rups/create/page.tsx`

### Backend

- роуты РУПов:
  - `backend/pkg/handler/handler.go`
- создание РУПа:
  - `backend/pkg/handler/rup_handler.go`
  - `backend/pkg/service/rup_service.go`
- генерация второго языка запускается автоматически после `CreateRup`, если передан `sourceLanguage`
- статусы длительного процесса уже хранятся через Redis-подобный механизм внутри `rup_service.go`

### Document rendering service

- сейчас сервис умеет генерировать `.docx` для РУПа, но не умеет парсить загруженный `.docx`
- точка расширения:
  - `document-rendering-service/app/main.py`
  - `document-rendering-service/app/services/rup.py`

## Что видно по текущему примеру `.docx`

Из примера файла явно читаются и подходят для детерминированного парсинга:

- название модуля
- специальность
- квалификация
- форма обучения
- общее количество часов
- курс
- группа
- разработчик(и)
- табличная часть с дисциплинами/темами/часами
- пояснительная записка и связанные текстовые блоки

Вывод: для такого формата лучше делать не AI-импорт, а обычный парсер `.docx` по таблицам, подписям и якорным строкам.

## Главные ограничения текущей реализации

Сейчас импорт в желаемом виде не получится без доработок.

### 1. `studyYear` и `course` сейчас обязательны

Сервис создания РУПа валидирует:

- `studyYear` обязателен
- `course` должен быть в диапазоне `1..4`

Файл:

- `backend/pkg/service/rup_service.go`

Кроме этого в БД:

- `rups.course INT NOT NULL CHECK (course BETWEEN 1 AND 4)`
- `rups.study_year TEXT NOT NULL`

Файл:

- `shared/atlas/schema.sql`

Если по бизнес-требованию эти поля после импорта должны быть пустыми, схему и backend-контракты нужно менять.

### 2. Текущая frontend-форма тоже требует эти поля

Форма создания/редактирования требует:

- `studyYear`
- `course`
- `groupId`

Файл:

- `frontend/src/app/rups/rup-schema.ts`

Значит импортированный черновик с пустыми полями нужно уметь:

- корректно открыть на просмотр
- корректно открыть на редактирование
- сохранить только после дозаполнения обязательных полей, если это нужно бизнес-процессу

### 3. Скачивание и утверждение РУПа завязано на `groups`

Сейчас генерация `.docx` и часть approval flow ожидают, что у РУПа есть хотя бы одна группа.

Файл:

- `backend/pkg/service/rup_service.go`

Если после импорта `groups = []`, то для таких РУПов надо:

- запрещать скачивание/утверждение, пока пользователь не заполнит группу
- явно показывать это в UI

### 4. `CreateRup` сейчас может запустить language generation

Для импорта это не нужно. Импортируемый РУП должен:

- создаваться без перевода
- сохраняться как `DRAFT`
- оставаться в исходном языке файла

## Рекомендуемый MVP

### Пользовательский сценарий

1. Пользователь открывает новую страницу `/rups/import`
2. Загружает `.docx`
3. Frontend создает импорт-задачу и показывает экран прогресса по этапам
4. Backend отправляет файл в `document-rendering-service`
5. `document-rendering-service` парсит файл и возвращает нормализованный JSON
6. Backend создает РУП в базе в статусе `DRAFT`
7. Поля `groups`, `study_year`, `course` остаются пустыми
8. Frontend редиректит пользователя на созданный РУП

### Что именно сохраняем в MVP

- `name`
- `type`
- `studyForm`
- `sourceLanguage`
- `explorationNote`
- `disciplines`
- `topics`
- `totalHours`
- `teacher` = текущий пользователь
- `status` = `DRAFT`

Пока не заполняем:

- `groups`
- `studyYear`
- `course`

## Архитектурный план

### Этап 1. Уточнить контракт импорта

Нужен отдельный DTO для импорта, а не прямой reuse текущего `CreateRupRequest`.

Рекомендуемый ответ парсера:

- `name`
- `type`
- `studyForm`
- `sourceLanguage`
- `courseRaw`
- `studyYearRaw`
- `groupsRaw`
- `specialtyRaw`
- `qualificationRaw`
- `developersRaw`
- `explorationNote`
- `disciplines`
- `warnings[]`

Почему так:

- часть значений нужно извлечь из файла, но не записывать в текущие поля БД
- часть значений может быть распознана неуверенно
- пользователю полезно видеть предупреждения после импорта

### Этап 2. Добавить backend flow для import job

Новые точки:

- `POST /rups/import`
- `GET /rups/import/:jobId`

`POST /rups/import`:

- принимает `multipart/form-data`
- проверяет расширение и размер файла
- создает `jobId`
- запускает фоновую обработку
- возвращает `202 Accepted`

`GET /rups/import/:jobId`:

- возвращает статус задачи
- этап
- процент
- ошибку
- `rupId`, если импорт завершен

Для хранения статуса лучше переиспользовать подход из `language generation`:

- Redis
- статусы `queued | running | completed | failed`
- этапы по аналогии с `rup_service.go`

Рекомендуемые этапы:

1. `upload_received`
2. `sending_to_parser`
3. `parsing_document`
4. `normalizing_payload`
5. `creating_rup`
6. `completed`

### Этап 3. Добавить парсер в `document-rendering-service`

Новая точка:

- `POST /parse-rup-docx`

Что делает сервис:

- принимает `.docx`
- читает таблицы и параграфы
- находит якорные поля по подписям
- собирает JSON
- не переводит текст
- не пишет ничего в БД

Почему сюда:

- сервис уже работает с `.docx`
- уже содержит зависимости для Word-документов
- логически это самое близкое место для парсинга документа

Рекомендуемая реализация:

- новый модуль `document-rendering-service/app/services/rup_import.py`
- парсинг без AI
- основной подход: поиск табличных секций по фиксированным заголовкам

### Этап 4. Нормализация на backend

Backend после ответа парсера должен:

- привести `studyForm` к enum проекта
- определить `type`
- подготовить `LocaleText`
- вычистить пустые дисциплины/темы
- валидировать часы
- подготовить `CreateRupRequest`-подобную структуру

Важно:

- `sourceLanguage` нужно передавать как исходный язык файла
- но `CreateRup` нельзя вызывать в виде, который запустит перевод

Лучше сделать отдельный метод в service-слое, например:

- `CreateImportedRup(ctx, req ImportParsedRupRequest)`

Он должен:

- не запускать `language generation`
- создавать запись сразу как `DRAFT`
- разрешать пустые `groups`, `studyYear`, `course`

### Этап 5. Изменить модель данных

Если требование “оставить пустыми `groups`, `study_year`, `course`” остается в силе, нужны изменения схемы:

- `course` сделать nullable
- `study_year` сделать nullable
- проверить весь backend/frontend на работу с `null`

Без этого импорт в текущем виде противоречит схеме БД.

Минимально затронутся:

- `shared/atlas/schema.sql`
- SQL queries / sqlc models
- `backend/pkg/service/rup_service.go`
- frontend types для `IRup`, `ICreateRupRequest`, edit/view страниц

### Этап 6. Добавить frontend страницу импорта

Новая страница:

- `/rups/import`

Что должно быть на странице:

- `input` для `.docx`
- описание формата
- кнопка загрузки
- список ограничений
- ошибки валидации файла

После отправки:

- переход на страницу ожидания импорта
- polling статуса задачи
- этапы и прогресс

UI можно строить по аналогии с:

- `frontend/src/app/rups/[id]/language-generation/page.tsx`

### Этап 7. Доработать просмотр и редактирование импортированных РУПов

Нужно, чтобы импортированный `DRAFT`:

- открывался без падений
- показывал пустые `group/course/studyYear` корректно
- явно подсказывал пользователю, что документ импортирован и требует дозаполнения

Желательно:

- баннер в `RUP view`: “РУП импортирован из файла, проверьте и заполните обязательные поля”
- отключить `download` и `approve`, пока нет группы

## Что лучше не делать в MVP

- не пытаться поддержать все возможные шаблоны `.docx`
- не добавлять AI-парсинг как основной путь
- не объединять импорт с текущим `POST /rups`
- не запускать автоперевод сразу после импорта

## Риски

### 1. Формат загружаемых РУПов может отличаться

Решение:

- в MVP поддержать 1-2 типовых шаблона
- возвращать `warnings`
- при сильном расхождении падать с понятной ошибкой

### 2. Потеря данных, которые нельзя положить в текущую схему

Например:

- сырой текст группы
- специальность
- квалификация

Если эти поля нельзя записывать в текущие колонки, нужно решить отдельно:

- либо хранить `raw import metadata`
- либо честно не сохранять их и показать это пользователю

### 3. Неполный РУП после импорта

Так как `groups/studyYear/course` остаются пустыми, часть функций системы временно будет недоступна.

Это нормально для `DRAFT`, но должно быть явно отражено в UX.

## Рекомендуемая последовательность работ

1. Зафиксировать бизнес-решение по `course` и `studyYear`: действительно ли они должны храниться пустыми в БД.
2. Зафиксировать контракт `ImportParsedRupRequest` и формат ответа import job status.
3. Реализовать `POST /parse-rup-docx` в `document-rendering-service`.
4. Реализовать import job в backend с прогрессом и polling.
5. Добавить отдельный service-метод создания импортированного РУПа без перевода.
6. Внести миграции и обновить типы, если `course/studyYear` становятся nullable.
7. Сделать `/rups/import` и страницу ожидания.
8. Доработать view/edit для импортированных черновиков.
9. Добавить тесты на parser + backend import flow.

## Открытые вопросы, которые нужно закрыть до реализации

1. `course` и `studyYear` должны быть `null` в БД или просто не участвовать в бизнес-логике до ручного дозаполнения?
2. Нужно ли сохранять сам исходный `.docx` в MinIO как “source document”?
3. Нужно ли хранить `raw import metadata`, если часть полей не пишется в текущую схему?
4. Поддерживаем только русский шаблон, или русский/казахский с первого релиза?
5. Нужно ли после импорта сразу открывать edit mode вместо обычной страницы просмотра?

## Итог

Импорт РУПа в проект хорошо ложится на текущую архитектуру, но это не “маленький endpoint”.

Минимально нужны:

- новый frontend flow `/rups/import`
- новый backend import job с прогрессом
- новый parser endpoint в `document-rendering-service`
- отдельная логика создания импортированного `DRAFT`
- вероятно, изменение схемы БД и типов, если `course` и `studyYear` действительно должны быть пустыми

Главный технический вывод после изучения проекта: критичная часть работы не в загрузке файла, а в согласовании модели данных с требованием “создать РУП, но оставить часть обязательных полей пустыми”.
